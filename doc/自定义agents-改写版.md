# 自定义 Agents 低成本方案（改写版）

## 一、目标

这份方案要解决的不是“是否使用自动化”，而是：

1. 如何在保证流程可运行的前提下控制大模型成本。
2. 如何避免把系统做成“看起来能跑、实际上难维护”的高耦合流水线。
3. 如何在后续扩展到批量任务、自动调度、并发执行时，仍然具备可观测性和可维护性。

简化结论如下：

> 长期可行的省钱方式，不是绕过 API，也不是依赖网页自动化，而是：
> 合理拆分流程、按步骤选模型、减少无效调用、缓存可复用结果，并对每一步做成本与质量追踪。

---

## 二、先澄清一个核心问题

自动化系统一旦建立，通常会放大调用次数、上下文长度和中间结果数量，因此总成本往往会上升。这是正常现象。

真正需要优化的，不是“绝对不花钱”，而是下面三件事：

1. 哪些步骤必须用强模型。
2. 哪些步骤可以用小模型或本地模型替代。
3. 哪些步骤其实不该重复执行。

换句话说，目标不是“零成本”，而是“把高成本能力只用在必要的位置”。

---

## 三、关于“网页自动化省钱”的判断

如果方案打算通过自动操作 ChatGPT 或类似网页界面来节约成本，这条路不适合做长期主方案。

原因不是单一的“价格问题”，而是以下几点：

1. 成本并不一定更低。网页背后仍然是模型调用，只是计费方式、额度限制和节流规则不透明。
2. 稳定性差。页面结构、登录状态、风控策略、交互细节一变，自动化脚本就可能失效。
3. 难扩展。网页方案不适合批量任务、自动调度、严格并发控制和可重复执行。
4. 难审计。正式系统通常需要保留输入、输出、重试记录和步骤成本，网页自动化不利于做标准化追踪。

因此：

> 网页自动化可以用于临时验证、人工辅助或早期原型，但不应作为正式生产链路的核心依赖。

---

## 四、成本主要烧在哪里

以“选题 -> 故事 -> 分镜 -> prompt -> 出图”为例，主要成本通常集中在以下部分。

### 1. 高成本步骤

高成本通常来自“长文本生成 + 高不确定性决策”：

1. 故事生成。
2. 分镜拆解。
3. 多轮反复修改。

这些步骤的共同特点是：

1. 输入上下文长。
2. 输出较长。
3. 容易因为一次结果不满意而重复调用。

### 2. 中成本步骤

中成本通常来自“结构整理和风格转换”：

1. prompt 生成。
2. 文案改写。
3. 结果格式化。

这类步骤未必单次昂贵，但执行次数多时会积累明显成本。

### 3. 低成本步骤

低成本通常是“规则明确、格式固定、可本地执行”的步骤：

1. 模板填充。
2. 字段校验。
3. 结果转 JSON。
4. 本地图像工作流调度。

注意：

> “ComfyUI 基本不要钱”只在本地已有硬件、且忽略电费与设备占用成本时近似成立。
> 如果使用云 GPU，这部分也会成为明确成本项。

---

## 五、可行的核心优化方向

### 1. 分层选模

不要把所有步骤都交给最强模型。

更合理的方式是：

| 步骤 | 建议模型策略 |
| --- | --- |
| 题材判断、故事框架 | 强模型 |
| 分镜拆解、镜头扩写 | 中等模型 |
| prompt 组装、格式整理、标签补全 | 小模型或本地模型 |
| 校验、去重、字段修复 | 规则引擎或脚本 |

原则不是“强模型只调用一次”，而是：

> 强模型尽量少用，只放在高价值、高不确定性、替代失败代价高的环节。

### 2. 减少无效调用

“减少调用次数”是有效方向，但不能理解成“所有步骤都尽量并成一次调用”。

真正应该减少的是：

1. 明明可复用却重复执行的调用。
2. 没有校验导致的返工调用。
3. 步骤划分过细、每步信息增量很小的调用。

不应该盲目减少的是：

1. 需要独立校验的关键步骤。
2. 容易失败且需要单独重试的步骤。
3. 需要结构化中间结果供后续复用的步骤。

也就是说：

> 少调用是方向，不是绝对规则。减少无效调用，比单纯压缩调用次数更重要。

### 3. 模板化

不要让模型每次都从零推断输出结构。

正确做法是：

1. 固定输入模板。
2. 固定输出字段。
3. 对风格、长度、镜头数、角色设定做硬约束。

模板化的作用有三个：

1. 降低 token 浪费。
2. 提高结果一致性。
3. 降低重试率。

### 4. 缓存复用

缓存是必要能力，但不能写成简单的 `cache[input] = result]`。

正式可用的缓存键至少应考虑：

1. 标准化后的输入内容。
2. prompt 模板版本。
3. 使用的模型名。
4. 关键参数，例如温度、输出格式、镜头数量。
5. 输出 schema 版本。

否则会出现下面的问题：

1. 模板更新后仍命中旧结果。
2. 换模型后结果混用。
3. 输出结构变化后缓存污染。

### 5. 控制输出长度

限制输出长度是有效方法，但要明确边界。

建议限制的是：

1. 故事摘要长度。
2. 分镜数量。
3. 单镜头描述最大字数。
4. prompt 的固定字段范围。

不建议一味压缩到极短，因为过短会让后续步骤信息不足，最终导致返工。

## 六、哪些原始说法需要修正

### 1. “调用 1 次 2000 token 一定比调用 5 次 1000 token 更便宜”

这个说法不成立。

是否更便宜，取决于：

1. 输入与输出 token 分别如何计费。
2. 单次长上下文是否引入额外冗余。
3. 长调用失败后的重试成本。
4. 合并后是否降低可控性，导致返工更多。

因此应改成：

> 在不损失可控性和复用性的前提下，减少低价值拆分通常有利于降低成本。

### 2. “一步输出故事 + 分镜 + prompt”

这个思路只适合原型期，不适合稳定生产。

原因如下：

1. 中间结果不可校验。
2. 任一环节出错都要整段重跑。
3. 无法只替换其中某一步模型。
4. 不利于缓存复用。

更稳妥的方式是：

1. 故事大纲。
2. 分镜结构化输出。
3. prompt 组装。

这三步可以优化边界，但不建议完全揉成一步。

### 3. “ComfyUI 免费”

应改成：

> 本地部署时边际成本较低，但仍存在硬件、功耗、维护和排队成本；如果走云 GPU，则是明确计费项。

### 4. “节省 60% 到 80%”

这个数字只能作为经验范围，不能直接写成结论。

更严谨的说法是：

> 如果原始流程存在强模型滥用、重复调用和缺少缓存的问题，引入分层选模、模板化和缓存后，通常有机会显著下降成本；实际降幅需要结合模型价格、任务长度、失败率和复用率测算。

## 七、推荐的落地架构

建议把流程拆成可验证、可缓存、可单独重试的几个阶段：

```text
输入需求
  ->
故事大纲生成
  ->
分镜结构化生成
  ->
prompt 组装与风格约束
  ->
图像/视频生成
  ->
质量检查与人工审核
```

### 1. 故事大纲生成

目标：

1. 产出短而稳定的故事骨架。
2. 明确角色、情绪、时空背景和冲突。

建议：

1. 用强模型。
2. 严格限制长度。
3. 产出摘要而不是长篇正文。

### 2. 分镜结构化生成

目标：

1. 把故事转为固定字段的镜头列表。
2. 每个镜头包含场景、主体、动作、机位、光影、情绪等字段。

建议：

1. 输出 JSON 或固定表格结构。
2. 加字段校验。
3. 允许失败时只重跑当前步骤。

### 3. prompt 组装

目标：

1. 按图像模型需要的格式拼装提示词。
2. 统一风格和禁用项。

建议：

1. 尽量模板化。
2. 可优先尝试小模型或本地模型。
3. 对常用风格做预设。

### 4. 图像或视频生成

目标：

1. 把文本结果转成最终素材。
2. 控制生成参数一致性。

建议：

1. 保存工作流参数。
2. 为每次生成保留元数据。
3. 记录失败原因和重试次数。

### 5. 质量检查

目标：

1. 发现角色漂移、风格偏移、字段缺失、镜头不连贯等问题。

建议：

1. 先做规则校验。
2. 再做模型校验。
3. 最后保留人工抽检入口。

## 八、正式方案里必须补充的工程能力

如果缺少下面这些能力，系统即使能跑，也很难稳定运营。

### 1. 可观测性

每一步至少记录：

1. 输入摘要。
2. 使用模型。
3. token 消耗。
4. 耗时。
5. 是否命中缓存。
6. 是否重试。
7. 最终状态。

### 2. 幂等与重试

对于可重复执行的任务，要支持：

1. 同任务重复提交不产生脏数据。
2. 单步骤失败后局部重试。
3. 超时、中断后可恢复执行。

### 3. 版本管理

至少为下面内容设版本号：

1. prompt 模板。
2. 输出 schema。
3. 模型配置。
4. 风格预设。

### 4. 质量评估

至少定义一些基本指标：

1. 平均每条任务成本。
2. 平均重试次数。
3. 分镜通过率。
4. prompt 可用率。
5. 最终素材人工通过率。

没有这些指标，就无法判断“优化”是否真的有效。

---

## 九、建议的实施顺序

不要一上来追求极限省钱，优先级建议如下：

1. 先跑通最小闭环。
2. 再让每一步输出稳定、可校验。
3. 再加入缓存和小模型替换。
4. 最后再做精细成本优化和并发扩展。

换句话说：

> 先解决“能不能稳定产出”，再解决“能不能更便宜地稳定产出”。

---

## 十、最终结论

这类自定义 Agents 或自动化内容流水线方案是可行的，但前提是：

1. 不把网页自动化当成长期正式链路。
2. 不把“减少调用次数”误解为“尽量一步做完所有事”。
3. 不把缓存理解成简单字符串映射。
4. 不把经验数字直接当成成本结论。

真正可靠的方案应当具备以下特征：

1. 强模型只用于关键决策点。
2. 中间结果结构化。
3. 每一步可缓存、可重试、可替换。
4. 成本、质量、失败率都可追踪。

如果按这个方向设计，方案不仅可行，而且更容易从“能跑的脚本”升级成“可维护的系统”。
